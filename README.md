# Avia

Микросервис для поиска авиабилетов и управления их бронированием. HTTP API обслуживает поиск городов, поиск доступных билетов и просмотр статуса бронирования. При настройке Kafka сервис также принимает команды резервирования и отмены и публикует изменения статуса.

## Архитектура

Код разделён по слоям: `delivery` принимает внешние запросы и преобразует DTO, `domain` содержит модели и бизнес-правила, `infra` отвечает за конфигурацию и интеграции, а `app` собирает компоненты и управляет их жизненным циклом.

```text
cmd/avia/                 Точка входа: конфигурация, сигналы завершения, запуск приложения
internal/
  app/                    Сборка приложения, запуск HTTP и Kafka, graceful shutdown
    rest/                 Жизненный цикл HTTP-сервера
    kafka/                Жизненный цикл Kafka consumer/producer
  delivery/
    rest/                 HTTP-маршруты, обработчики и REST DTO
    kafka/                Kafka consumer, handler, producer и DTO сообщений
  domain/
    models/               Модели аэропорта, города, рейса и билета
    rules/                Допустимые статусы и переходы бронирования
    services/avia/        Сценарии чтения и изменения билетов
  infra/
    config/               Чтение YAML и значения конфигурации по умолчанию
    db/                   Подключение к PostgreSQL и запуск миграций
    repos/                PostgreSQL-реализация репозитория билетов
    observability/        Логирование
migrations/               Миграции схемы и тестовые данные
config/                   Примеры конфигурации и Docker-файлы
```

При старте `internal/app` загружает конфигурацию, применяет миграции, создаёт пул PostgreSQL и репозиторий, затем связывает его с доменными сервисами и HTTP-обработчиками. Kafka-компоненты создаются только если в конфигурации заданы брокеры.

## HTTP API

| Метод и путь | Параметры | Назначение |
|---|---|---|
| `GET /cities?query=...` | `query` — необязательная строка поиска | Возвращает список городов |
| `GET /tickets?from=...&to=...` | `from`, `to` — обязательные города отправления и прибытия | Возвращает доступные билеты на маршрут |
| `GET /tickets/{ticketId}/reservation-status` | `ticketId` — положительный ID билета | Возвращает статус бронирования и время его обновления |

Ошибки API возвращаются в JSON с полями `code` и `message`. Некорректные параметры приводят к `400`, отсутствующий билет — к `404`, внутренняя ошибка — к `500`. Поиск билетов не возвращает отменённые рейсы и билеты, которые уже не имеют статуса `available`.

## Бизнес-логика и данные

`TicketQueryService` отвечает за реализацию синхронного API `TicketCommandService` в свою очередь отвечает за бронь и отмену брони.

Репозиторий в `internal/infra/repos` выполняет запросы PostgreSQL к таблицам аэропортов, рейсов и билетов. Изменения структуры БД оформляются новой последовательной SQL-миграцией в `migrations/`, а не ручным изменением уже применённой миграции.

## Запуск и разработка

Скопируйте `config/dev.yaml.example` в `config/dev.yaml` и `config/docker/pg.env.example` в `config/docker/pg.env` и задайте свои значения. Запустите сервис командой `make docker-up`

Для запуска не через docker и корректной работы lsp в вашей IDE рекомендуется установить go версии указанной в `go.mod`. Для запуска через docker достаточно иметь docker установленный в системе.

Приложение по умолчанию читает `config/dev.yaml`; другой путь можно указать через переменную окружения `CONFIG_PATH`. Сборка — `make build`, линтер — `make lint`. Д

Для разработки новой функции рекомендуется следовать принципу инверсии зависимостей: внешний адаптер (`delivery`) вызывает доменный сервис, сервис опирается на интерфейс репозитория, а реализация доступа к PostgreSQL остаётся в `infra`. Покрывайте новые бизнес-сценарии тестами рядом с сервисом (`*_test.go`).
